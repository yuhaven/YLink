# CastPane 复盘：为什么做不成，以及后续怎么避免

> 本文档用于沉淀经验并可直接拆成 Skill。结构固定为 **现象 → 根因 → 解决方案 → 可执行规则**。
> 适用对象：后续任何“桌面端工具 + 设备投屏/控制”类项目。

---

## 0. 一页结论

| 你指出的问题 | 我的根因（一句话） | 归类 |
|---|---|---|
| 要求“参考其他投屏软件设计”，没做 | 我把“参考”当成了审美描述，没有把它变成可验收的动作 | 需求执行 |
| 要求“自动测试通过后再交付”，没做到 | 我的测试验证的是“我写的代码能跑”，不是“用户的操作能成” | 验收体系 |
| 控制台设置点击后不生效 | 滑块控件根本没接“变更”事件，只改了内存值 | 实现缺陷 |
| 窗口拖动后弹回 | 测试遗留的 `lockPosition=true` 被写进发布包配置 | 环境/发布 |
| 屏幕亮度有问题 | 这个功能**从未实现**，只有“保持亮屏”，且被配置关掉了 | 需求缺失 |
| 极简主义、插件化没实现 | 把“插件化”当成进程隔离，把“极简”当成窗口小 | 架构 |
| 功能不全就让你测试 | 我把“能启动”当成“可交付”，没有 DoD 和门禁 | 流程 |
| 没优先做无线投屏 | 技术惯性：scrcpy 有线最省事，没做用户旅程 | 产品思维 |

**最核心的一条**：我一直在用“实现视角”推进，而不是“使用视角”。所有问题都是这一条的下游表现。

## 1. 问题一：明确要求没完成

### 1.1 “参考其他投屏软件的设计”

**现象**：导航条做成了压在画面上的悬浮层；你指出后我才改成窗口外工具条。你问我“真的查看了吗”——没有。

**我实际做了什么**：凭对“悬浮控制条”的印象直接实现，没有打开任何一个投屏软件做对照，也没有输出对比结论。

**为什么没做**：
1. 我把“参考设计”理解成“把按钮画得好看点”，没有意识到它是**布局与信息层级**的要求。
2. 我的流程里没有“竞品基线”这一步：需求进来直接进实现。
3. 我没有把“参考”转成可验收项（例如“与 XX 软件的工具栏位置一致：窗口外、同宽、贴底”）。

**解决方案**：
- 任何涉及界面的需求，先产出 **竞品拆解表**（软件 / 截图 / 控件位置 / 层级 / 交互），再动手。
- 拆解表必须包含“我们的对照结论”，并由你确认后再实现。
- 界面验收用**截图对比**，不是文字描述。

**规则 R1**：出现“参考/类似/像 XX 那样”的字样，必须先交付竞品拆解表，否则不进入实现。

### 1.2 “自动测试通过后再交付”

**现象**：我多次说“已修复、PASS”，你实际使用时仍然有问题。这不是巧合，是测试体系的问题。

**三个具体缺陷的根因（都有证据）**：

#### (a) 控制台设置点击后不生效

- 证据：`apps/desktop/src/main.ts` 的 slider 分支只有 `input` 监听，**没有 `change` 监听，也没有调用 `onChange`**。也就是说拖动“分辨率/帧率”只会改内存里的值，既不保存也不下发。
- 叠加原因：`scheduleApply` 只在“当前有会话”时才下发；没有会话时改设置完全不反馈，看起来像坏了。
- 第三个原因：即使下发成功，插件对非窗口级设置**重启会话**（约 1 秒黑一下），用户感知是“点了没反应/闪一下”。

**为什么没测出来**：我的 E2E 只驱动了“下拉框 + 投屏按钮”，从没驱动过滑块和开关；单测只覆盖 Rust 侧参数拼接。

#### (b) 窗口拖动后弹回原位置

- 证据：`dist/CastPane/settings.json` 里 `lockPosition: true`、`stayAwake: false`。这是早期测试写入后被一起打包的。
- 机制：`lockPosition=true` 会启动 `window::enforce` 线程，把窗口拉回设定位置，所以“拖动就弹回”。
- 为什么没测出来：我每次测试前只删 `settings.json`，但**打包脚本又把测试产物一起装进 zip**；而发布包里的默认值没有人校验。

#### (c) 屏幕亮度有问题

- 事实：**这个功能不存在**。插件只有“保持亮屏（stayAwake）”，没有亮度控制。
- 而且你的配置里 `stayAwake: false`，所以 `--stay-awake` 根本没传，手机自然会息屏/变暗。
- 为什么：需求里没有“亮度”这一项，是我没有把“屏幕相关”需求补全，也没有在面板上明确“这里只有常亮、没有亮度”。

**为什么整体没测出来**：
1. 我的验收标准是“命令返回成功 / 窗口出现”，不是“用户改完之后看到变化”。
2. 测试脚本自己构造参数，绕过了界面；界面层几乎没有自动化。
3. 测试环境不隔离：配置、进程、旧产物都会互相污染。
4. 我把“跑通一次”当成“稳定可用”，没有回归集。

**解决方案（三层门禁）**：

| 层 | 覆盖 | 必须断言 |
|---|---|---|
| L1 单元 | 参数拼接、协议、状态机 | 纯函数输出 |
| L2 协议 | 插件 JSON-RPC 全流程 | `session.state`、`applied` 字段 |
| L3 UI E2E | **真实点击界面** | 窗口比例、控件可见性、耗时、配置落盘 |

交付前必须跑一条命令，全绿才允许说“完成”：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\gate.ps1
```

（`gate.ps1` 待实现：清理环境 → cargo test → 打包 → E2E → 校验发布包默认配置）

**规则 R2**：任何“已修复”必须有可观察证据（截图/数值/日志），否则只能说“已改，待验证”。
**规则 R3**：界面控件的变更必须有自动化用例；没有用例的控件不允许出现在面板上。
**规则 R4**：发布包必须校验默认配置（`lockPosition=false`、`stayAwake=true`），测试产物不得进入 zip。

### 1.3 修复计划（本轮）

| 缺陷 | 修复 | 验收 |
|---|---|---|
| 滑块不生效 | 增加 `change` 监听 → `onChange` → `scheduleApply` | 拖动分辨率后 1 秒内投屏重启，日志出现 `applied=restart` |
| 拖动弹回 | 发布包重置 `lockPosition=false`；面板上该开关旁标注“关闭后才能拖动” | 拖动后位置保持 |
| 亮度 | 明确不提供亮度；把“保持亮屏”改名为“保持手机常亮”，默认开 | 投屏后手机不息屏 |

## 2. 问题二：偏离“极简主义 + 插件化”

### 2.1 现状（证据）

- 面板一屏塞了 9 个元素：文本、2 个锁定开关、音频、常亮、分辨率、帧率、分隔线、按钮；窗口 480×760 仍然要滚动。
- 所有设置**硬编码在 `plugins/android/plugin.json`**，核心只负责“按 schema 画控件”。
- “插件化”目前只体现在**进程隔离**（独立 exe + JSON-RPC），UI 与能力都没有真正的可插拔边界。

### 2.2 为什么

1. **把插件化理解成“拆进程”**：我完成了协议和 sidecar，就认为插件化达成；但插件化的价值是“能力可增删、界面可裁剪”，不是“多一个 exe”。
2. **把极简理解成“窗口小”**：我压缩的是尺寸，不是信息量。真正的极简是**默认路径上没有选择**。
3. **没有信息架构**：每个新需求就加一行控件，从不删减、不分层。
4. **没有设计稿**：直接写 DOM，导致布局是被需求推着长出来的。

### 2.3 解决方案

**极简的具体定义（可验收）**：
- 首屏只允许三块：**设备列表（含一个主按钮）**、**一行状态**、**一个「更多」入口**。
- 首屏可交互元素 ≤ 5 个。
- 任何设置项必须有“默认值 + 为什么需要改”的一句话，否则不进首屏。

**插件化的具体定义（可验收）**：
- 核心不含任何业务词（不出现“分辨率/音频/旋转”等字样）。
- 插件通过 `capabilities` 声明能力，核心只调度不实现。
- 插件可贡献：设置项、动作、状态；核心只渲染白名单组件（switch/select/slider/button）。
- 下一阶段：插件自带独立设置页（HTML 片段或独立窗口），核心只提供入口，彻底解除 schema 耦合。

**规则 R5**：首屏元素数量是硬指标；新增控件必须同时说明“删掉哪个”。
**规则 R6**：核心代码不允许出现设备/媒体相关的业务名词。
**规则 R7**：插件的能力必须能在不重新编译核心的情况下增删。

## 3. 问题三：功能不全就交付测试

### 3.1 现象

- 我多次在你还没法完整使用时就请你“试试”，然后你来报告问题，我再修。
- 一个功能往往要 3-4 轮往返才能用。

### 3.2 为什么

1. **没有 Definition of Done**：我的完成标准是“编译通过 + 脚本不报错”。
2. **把用户当测试员**：因为我本地只验证了协议层，界面层验证成本高，就默认“用户点一下就知道”。
3. **没有功能冻结**：边加功能边改架构（窗口边框改了三次、方向逻辑改了三次）。
4. **没有回归**：修 A 坏 B（置顶修好后按钮置灰、导航条压画面）。

### 3.3 解决方案

**DoD（每个功能必须全部满足才算完成）**：
1. 用户路径可复现：按用户操作顺序能完成目标。
2. 自动化覆盖：L3 E2E 有对应用例且通过。
3. 失败可诊断：出错时日志/界面能指出原因。
4. 无回归：`gate.ps1` 全绿。
5. 文档同步：README + 面板文案更新。

**交付节奏**：
- 一个迭代只交付**一个可用闭环**（例如“无线连接 + 投屏 + 旋转”），不做半成品演示。
- 交付前我自己按用户路径完整走 3 遍（首次使用 / 二次使用 / 异常路径）。
- 交付说明必须写：本次能做什么、不能做什么、已知问题。

**规则 R8**：没有通过 DoD 的功能，不允许出现在交付说明里。
**规则 R9**：一次迭代只允许一个“未完成功能”在开发中，其余必须冻结。
**规则 R10**：交付前必须由我完成 3 场景自测，且贴出证据。

## 4. 问题四：反人类设计（没有优先无线投屏）

### 4.1 事实

- 当前只支持 USB（scrcpy over adb）。
- 无线能力只停留在方案文档里；AirPlay 引擎因为下载失败就搁置了。
- 手机要插线才能用——这在一堆无线投屏产品面前是倒退。

### 4.2 为什么

1. **技术惯性**：scrcpy 现成、USB 最稳，我就沿着最省力的路径走。
2. **没有用户旅程**：没有问“手机通常在哪、离电脑多远、是否边充电边看”。
3. **把“能跑”当“好用”**：USB 能跑通就默认需求满足。
4. **风险规避过度**：无线要处理配对/同网段/延迟，我回避了不确定性，选择确定但难用的方案。

### 4.3 解决方案

> **2026-11-16 更新**：本节写于目标机型确认前，其中「Android 11+ `adb pair`」的方案已被实机推翻。HUAWEI Mate 60（BRA-AL00）/ HarmonyOS 4.2.0 的开发者选项中没有「无线调试」，正确路径是 USB 一次 `adb tcpip 5555` + 同一 Wi-Fi `adb connect`。实际交付与证据见 `docs/wireless-cast-delivery.md`；下面的旧表仅保留为当时的分析记录。

**先画旅程，再选技术**：

| 场景 | 用户期望 | 技术路径 |
|---|---|---|
| 手机在手边、临时看 | 不插线，几秒连上 | Android 11+ `adb pair` 无线调试（同 Wi-Fi） |
| 手机在充电、想投屏 | 插线也可以，但别每次配置 | USB 作为保底 |
| iPhone 用户 | 直接 AirPlay | AirPlay 接收端（uxplay） |
| 不同网段/公共网络 | 扫码或 PIN | 中继/配对码 |

**优先级**：无线（adb pair）> USB > AirPlay > DLNA。
**验收**：从“打开电脑端”到“手机画面出现”≤ 15 秒，全程不插线。

**规则 R11**：涉及连接方式的需求，必须默认无线优先，USB 只作为兜底。
**规则 R12**：任何功能先写用户旅程（谁、在哪、做什么），再选技术。

## 5. 我自己的复盘（你没提但同样严重）

1. **反复改同一件事**：窗口边框改了 3 次（自绘→子类化→原生），方向逻辑改了 3 次。根因是没有先确认“平台能力边界”。
2. **过度承诺**：多次说“已修复”，实际只验证了协议层。这句话应该被“已验证/待验证”取代。
3. **不做设计稿**：界面靠需求堆叠，导致布局反复。
4. **测试污染环境**：settings.json、旧进程、旧产物反复干扰，甚至被打进发布包。
5. **缺少可观测性**：没有界面内日志面板，排查全靠 `%TEMP%\castpane.log`。
6. **忽略资源与性能**：8ms 轮询、两个额外窗口、每次设置变更重启整个会话，都没有度量。
7. **文档滞后**：README 与实际行为多次不一致（例如“切换方向需重新投屏”）。
8. **不考虑异常路径**：设备掉线、杀软拦截、无管理员权限、端口占用，都是你遇到才补。
9. **把“自动测试”做成“脚本能跑”**：没有断言用户可见结果。
10. **没有版本与回滚意识**：多次靠“重新打包”覆盖，缺少可回退的发布记录。

**对应规则**：
- **R13**：先确认平台能力（有无现成 API），再决定自研。
- **R14**：禁止说“已修复”，只能说“已验证（附证据）”或“已改待验证”。
- **R15**：界面需求先出线框/截图，确认后再写代码。
- **R16**：测试必须隔离环境（配置/进程/产物），并有清理脚本。
- **R17**：必须有界面内可查看的日志与诊断入口。
- **R18**：涉及重启会话的设置，必须评估并度量感知延迟。
- **R19**：文档与实现同一次提交更新。
- **R20**：每个发布包必须能回滚到上一版。

## 6. 可直接生成 Skill 的结构

建议 Skill 名称：`desktop-cast-feature-delivery`

### 6.1 触发条件
- 新增/修改桌面端工具的功能
- 涉及设备连接、窗口控制、设置面板
- 用户提出“参考 XX 软件”“自动测试后再交付”

### 6.2 必须执行的步骤（顺序不可跳过）

1. **需求澄清**：输出《需求卡》——用户旅程、成功标准（可观察）、非目标。
2. **竞品拆解**（若涉及界面/交互）：截图 + 控件位置 + 层级 + 对照结论，等确认。
3. **能力边界确认**：列出平台现成 API，标注“能用/不能用/需自研”。
4. **实现**：一次只动一层；核心零业务词。
5. **三层测试**：L1 单元 → L2 协议 → L3 真实 UI E2E。
6. **DoD 检查**：5 条全过。
7. **交付说明**：能做什么/不能做什么/已知问题/验证证据。
8. **复盘**：现象→根因→规则，写入本文件。

### 6.3 检查清单（复制即用）

```markdown
- [ ] 需求卡已写，成功标准是可观察量
- [ ] 涉及界面：竞品拆解表已确认
- [ ] 平台能力已确认，未自研已有能力
- [ ] 首屏交互元素 ≤ 5
- [ ] 每个控件都有变更→应用→验收用例
- [ ] L3 E2E 覆盖了用户真实点击路径
- [ ] 发布包默认配置已校验
- [ ] settings/进程/产物 已隔离清理
- [ ] 文档与实现同提交
- [ ] 交付说明写明“不能做什么”
```

### 6.4 反面模式（出现即打回）

- “应该可以了，你试试”
- “参考了 XX 风格”（无截图、无对照）
- 用协议测试代替界面验收
- 新增控件不删旧控件
- 核心代码出现业务名词
- 没有回滚路径的发布

## 8. 2026-11-16 追加：无线默认路径选错机型能力

### 8.1 现象

- 我把默认体验设计成 Android 11+「无线调试 / `adb pair` / 6 位配对码」，还写了配对向导。
- 目标机 HUAWEI Mate 60（BRA-AL00）是 HarmonyOS 4.2.0 / EMUI 14.2.0 / Android 12；开发者选项里**没有「无线调试」**（滚动到底也没有）。用户按向导会永远卡在第 1 步。
- 正确路径是 USB 一次 `adb tcpip 5555` + 同一 Wi-Fi `adb connect`；这条路径直到用户明确指出才成为默认。

### 8.2 根因

1. 把「Android 11+ 有无线调试」当成所有 Android 的通用能力，忽略了 OEM 定制系统会裁掉 AOSP 菜单。
2. 需求卡里没有写「目标机型 / 系统版本 / 现有菜单截图」，能力边界只查了通用文档，没有查这台手机。
3. 先写了配对向导和协议，再回头验证设备，顺序反了；导致 UI、文档、mock 都围绕一条不可用路径堆叠。
4. 把「USB 兜底」当成一句文案，没有把它做成首屏可完成的开通闭环。

### 8.3 规则

- **R21 先确认目标设备能力**：默认连接路径必须以目标机型实机截图/命令为证据；OEM 定制系统不能假设 AOSP 菜单存在。
- **R22 默认路径必须一步不少地走通**：如果目标设备上第一步就不存在，方案作废，不得用「其他 Android 可以」辩护。
- **R23 兜底也要闭环**：USB 兜底必须包含「发现 USB → 授权提示 → 读取 Wi-Fi IP → tcpip → connect → 可拔线 → 记住端点」的完整路径和失败原因。
- **R24 不把不可用路径做成 UI**：目标设备没有的入口（配对码/二维码/无线调试）不得出现在首屏、向导或文案里，只允许在「已知限制」中说明。
- **R25 先机型后协议**：技术选型顺序改为「目标机型能力 → 用户旅程 → 协议/引擎 → UI」，不得反过来。

### 8.4 本轮吸取后的做法

- 首屏只保留「设备 + 主按钮 + 一行状态 + 更多」，首次开通是 3 条 USB 步骤 + 一个「一键开启无线」进度层。
- 已记住端点自动重连；手机重启/换网后失败原因明确写「插一次数据线重新开启」。
- 配对码、二维码、无线调试在实现和文案中全部移除；`adb pair` 相关代码也从插件中删除。
- 真机无线画面已验证；UI 首次开通链路用 mock adb/scrcpy 做了 L3，真机 UI 点击路径因测试中切回 USB 后 Windows 未再枚举设备，标注为「已改，待真机验证」。

## 9. 2026-11-16 追加：AirPlay 引擎“装上了但不能用”与文件互传验收

### 9.1 现象

- 按固定 SHA-256 下载 uxplay-windows 2.0.0.1736，解压成功、进程能起，mDNS 也能看到 `CastPane`；但本机始终没有 AirPlay 监听端口，画面窗口也不会出现。
- 实际原因不是“引擎没下载”，而是发布 zip 缺 `libexec/gstreamer-1.0/gst-plugin-scanner.exe`，19 个 GStreamer 插件没有被扫描，H.264/D3D11 管线起不来；只检查 `uxplay-windows.exe` 是否存在会误判为“已就绪”。
- uxplay-windows 还依赖 Windows `Bonjour Service`；缺失时它弹自己的模态框，CastPane 看起来“启动成功”但什么都没发生。
- 文件互传 E2E 出现假通过：第一次 `Wait-Transfer done` 读到的是上一次 push 留下的 done，pull 还没开始就被当成完成；UIA 里文件行的 Name 是“文件名 + 类型 + 时间 + 大小”的整行文本，按精确文件名找不到；`ls -la /sdcard` 只列 symlink 本身，文件页把 `/sdcard` 显示成一个 21 B 文件。
- 机器上残留的 uxplay 进程让 AirPlay mock 生命周期测试报 `E_ALREADY_RUNNING`，`cargo test --workspace` 变红。

### 9.2 根因

1. 只把“引擎文件存在”当成“接收端可用”，没有检查解码链路（scanner + H.264/D3D11/playback 插件）。
2. 没有把 mDNS 服务、监听端口、防火墙放进同一个“接收端可被 iPad 发现”的判据。
3. E2E 的 transfer 探针只有 state，没有 transfer id；新传输开始前仍显示旧 done，导致“等待完成”立即返回。
4. UIA 的 Button Name 是聚合文本，不是文件名；测试按整串精确匹配，找不到行。
5. 真实设备命令语义没先验证：toybox `ls` 对 symlink 参数默认列链接本身，必须加尾斜杠或解引用。
6. 测试隔离只杀了 castpane/插件，没有隔离“开发机上真实 uxplay 正在跑”的情况；mock 引擎的会话被真实进程检查挡住。
7. 界面自动刷新在用户勾选文件后清空选择，下载按钮变灰；这不是测试问题，是真实可用性问题。

### 9.3 规则

- **R26 引擎就绪 = 解码链路就绪**：AirPlay 必须同时检查 uxplay、GStreamer scanner、H.264/D3D11/playback 插件、Bonjour 服务；任何一项缺失都禁用启动并给可执行修复入口。仅校验 exe 不算“装好”。
- **R27 发布 zip 缺件要补，不要只换下载途径**：固定哈希只能证明“下到的包没坏”，不能证明“包是完整的”。下载成功后跑一次真实探针（gst-inspect 关键 factory、启动后 mDNS/端口），缺件用第二来源补齐并再次校验。
- **R28 接收端状态以用户可观察量为准**：`waiting` = 进程在 + mDNS 在 + 端口在；`streaming` = 可见画面窗口出现。没有客户端证据不得写“iPad 已连接/已看见”。
- **R29 传输探针必须带稳定 id**：E2E 等待“新传输”时不能只看 state；至少带 transfer id，等待状态且 id 不同。UI 开始新传输时应立即把旧完成卡片替换为 running/pending。
- **R30 UIA 列表行用“列表容器 + 前缀”匹配**：文件行 Name 是聚合文本；必须在 `files-list` 容器内按“文件名 + 空格”前缀找，不能在整窗按精确名找，也不能把传输卡片里的同名文本当文件行。
- **R31 真实设备命令先验证语义**：`ls -la /sdcard` 会列 symlink 本身；列目录统一补尾斜杠，并加单测/真机回归。类似地，`stat`、`sha256sum`、`push/pull` 的输出格式都要以真机为准。
- **R32 测试钩子要隔离真实进程**：使用 mock 引擎时，跳过“本机已有真实 uxplay”的检查；E2E 开始前杀干净 castpane/插件/scrcpy/uxplay。否则测试会被开发机状态污染。
- **R33 自动刷新不能吃掉用户选择**：传输完成后刷新目录要么保留选择，要么只在明确点击刷新时做；不得在用户刚勾选文件后清空选择并置灰下载按钮。
- **R34 没有设备就写“待真机验证”**：本轮没有 iPad，交付说明只能写“已改，待真机验证”，并给出控制中心 → 屏幕镜像 → CastPane 的 5 步验收；不得用 mDNS 记录冒充画面证据。
