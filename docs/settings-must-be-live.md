# 经验：控制台的每个设置都必须实时反映到窗口

日期：2026-11-15 ｜ 触发问题：控制台形同虚设，改完设置没有反应

---

## 一、问题是什么

用户的原话是：

> 控制台上所有的设置都会实时地在窗口上反应出来，这是当前控制台的最大问题之一，这会让控制台完全没有实现控制台的功能。

也就是说，界面上的开关、滑块如果只是“存起来下次生效”，那它就**不是控制台，而是一个配置文件编辑器**。控制台的定义是：**操作 → 立刻看到结果**。

我们先后在这上面栽了三次：

| 设置项 | 之前的错误行为 | 用户的感受 |
|---|---|---|
| 画面方向 | 改完要重新点「投屏」 | “横竖屏不能用” |
| 总在最前 | 改了没反应，要重开 | “这个开关是坏的” |
| 分辨率/帧率 | 改了没反应 | 尚未反馈，但同样错误 |

---

## 二、为什么会这样（根因）

### 1. 架构上把“设置”当成了“启动参数”

scrcpy 的大部分参数（分辨率、帧率、音频、方向）只能在**进程启动时**传入。我最初的设计是：

```
界面改设置 → 存文件 → 下次 connect 时读取 → 启动 scrcpy
```

这个设计对“配置文件”是对的，对“控制台”是错的。控制台必须在**当前会话**上生效。

### 2. 没有建立“应用设置”的通道

插件协议里虽然写了 `settings.apply`，但实现是空的（直接回 ok）。界面也从不调用它。协议写了不等于实现了，更不等于验证了。

### 3. 没有把“实时”写进验收标准

我的验收是“设置文件里有这个值”，而不是“窗口在 1 秒内发生了变化”。前者容易通过，后者才是用户要的。

---

## 三、现在的实现

### 通道

```
界面控件变化
  → saveValues（写 settings.json）
  → scheduleApply（250ms 防抖）
  → Tauri 命令 apply_settings
  → 插件 settings.apply
```

### 插件侧策略（分级）

| 设置 | 生效方式 | 延迟 |
|---|---|---|
| 总在最前 | `SetWindowPos(HWND_TOPMOST / NOTOPMOST)`，不重启 | 立即 |
| 画面方向 | 换方向重启会话（scrcpy 无法旋转运行中的流） | ~1 秒 |
| 分辨率 / 帧率 / 音频 / 保持亮屏 | 重启会话 | ~1 秒 |

判断逻辑：先比较新设置与当前设置，**只有 `alwaysOnTop` 变化**就走实时路径；其余走重启路径，并在返回里注明 `applied: "live"` 或 `"restart"`，界面据此显示不同提示。

### 界面侧

- 任何控件变化都会触发 `scheduleApply`（滑块的抖动由 250ms 防抖处理）；
- 重启期间设置 `restarting = true`，这样会话 `stopped` 事件不会清空当前设备、也不会把投屏按钮置灰；
- 重启完成后 `streaming` 事件把 `restarting` 复位。

### 验证（真机）

```
initial:        topmost=False  x=1824
apply topmost:  {"applied": "live", "ok": true}
after topmost:  topmost=True   x=1824      ← 没有重启，位置也没变
apply maxSize:  {"applied": "restart", "ok": true}
after restart:  topmost=True   x=1824      ← 窗口重建，设置保留
```

## 四、顺带解决的两个交互问题

### 1. 控制台被投屏窗口遮住

投屏窗口原先居中，控制台也居中，必然重叠。现在投屏窗口**默认靠屏幕右侧**（`x = 屏宽 - 窗宽 - 40`），控制台保持居中，二者不重叠。

置顶仍然是一个开关，且现在**实时生效**：

- 默认关闭：投屏窗口不会盖住控制台；
- 打开：投屏窗口 `HWND_TOPMOST`，盖住一切（含控制台），适合全屏看剧；
- 关闭：立刻恢复普通层级。

### 2. 图标跟随窗口有延迟

悬浮按钮原先用 200ms 定时器跟随，拖动窗口时明显“追不上”。改为 **30ms** 定时器，并用 `SetWindowPos` 直接定位（不重绘、不激活），肉眼已看不出延迟。

图标从 `⟳` 文本换成 **Segoe MDL2 Assets 的 Rotate 字形**（与系统图标同源），在深色圆角底上更清晰。

## 五、沉淀成规则

1. **界面上的每个控件都必须有“应用”路径**。加控件时同时写：它如何作用到正在运行的实例，延迟多少，失败怎么提示。写不出来就别加这个控件。
2. **验收标准写“窗口发生了什么”，不是“存储里有什么”**。例如“勾选总在最前后 1 秒内窗口 `topmost=True`”。
3. **设置分级**：能实时改的（窗口样式、层级、位置）绝不重启；必须重启的（编码参数）要告知用户“正在应用”，并在重启后恢复会话状态。
4. **重启期间的界面状态要显式管理**：用 `restarting` 标志区分“用户关窗”与“我们主动重启”，否则按钮会被错误置灰。
5. **控制台永远优先可见**：新窗口默认不要压住控制台；需要置顶时由用户显式打开。

## 七、第四轮反馈的处理（2026-11-16）

| 需求 | 处理 | 结果 |
|---|---|---|
| 删除「总在最前」 | 设置项、面板开关、`--always-on-top` 传参、核心的 topmost 全部移除；投屏窗口默认靠右，控制台居中，二者不重叠 | 实测投屏 `topmost=False`，x=1824，控制台不遮挡 |
| 音频转发 | 手机是 Android 12（API 31），scrcpy 的音频转发要求 **API 33+**，设备侧无法转发 | 诊断面板新增 audio 检查，直接说明原因 |
| 跟随延迟 | 定时器 30ms → 专用线程 **8ms** 轮询 + `SetWindowPos` | 拖动时按钮跟随，肉眼无滞后 |
| 三键导航 | 投屏窗口右下角新增返回/桌面/多任务，点击执行 `adb shell input keyevent 4/3/187` | 实测点「桌面」后手机焦点从阅读 App 变为 launcher |

### 音频为什么改不了

`adb shell getprop ro.build.version.sdk` = **31（Android 12）**。scrcpy 启动日志明确写着：

```
Audio disabled: audio playback capture source not supported before Android 13
```

所以不是设置没生效，而是这台手机的系统不支持把应用声音交给 scrcpy。要求「切换音频不重启窗口」在 Android 13+ 上同样做不到——音频流属于会话的一部分，scrcpy 没有运行中增删音频流的接口。届时的做法只能是：默认开启音频转发，用「静音/取消静音」在 PC 侧控制（相当于实时，不重启）；这需要额外的 WASAPI 控制层，本轮未做。

> 结论：当前设备上“音频在电脑播放”不可实现；诊断面板会直接显示这条原因，避免再被误认为开关坏了。

## 八、验收清单（以后每个设置项都要过一遍）

- [ ] 改完后 1 秒内，投屏窗口有可见变化
- [ ] 变化不需要重新点「投屏」
- [ ] 重启类设置会显示“正在应用”，完成后按钮状态正常
- [ ] 关闭投屏窗口后，按钮恢复可点
- [ ] 控制台与投屏窗口默认不重叠
