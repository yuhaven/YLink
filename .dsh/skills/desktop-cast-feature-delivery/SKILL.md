# 桌面投屏功能交付

用「使用视角」推进，不要用「实现视角」。下面步骤必须按顺序执行，不可跳过。完整规则见 [references/rules.md](references/rules.md)。

## 1. 需求澄清

先输出《需求卡》，模板见 [references/requirement-card.md](references/requirement-card.md)。成功标准必须是可观察量，例如：「点『投屏』后 3 秒内出现窗口，宽高比约 2.2」。

有歧义的表述（如「不能随便拖动」）至少给出两种解释让用户挑，对齐前不写代码。

## 2. 竞品拆解（涉及界面或交互时必做）

出现「参考 / 类似 / 像 XX 那样」的字样，必须先交付竞品拆解表：软件、截图、控件位置、层级、交互、我们的对照结论。等用户确认后再实现。界面验收用截图对比，不用空口描述。

## 3. 能力边界

先列出平台现成 API，标注「能用 / 不能用 / 需自研」。禁止在未确认平台能力时反复自研同一问题。跨进程窗口不要用 `SetWindowLongPtrW(GWLP_WNDPROC)` 子类化。

## 4. 实现约束

- 一次只动一层。一次迭代只允许一个未完成功能在开发中，其余冻结。
- 首屏只允许三块：设备列表（含一个主按钮）、一行状态、一个「更多」入口。首屏可交互元素 ≤ 5。新增控件必须同时说明删掉哪个。
- 核心代码不允许出现设备或媒体业务名词（分辨率、音频、旋转等）。能力由插件 `capabilities` 声明，核心只调度和渲染白名单组件。
- 连接方式默认无线优先，USB 只作兜底。先写用户旅程再选技术。
- 控制台每个控件必须有「应用到当前会话」的路径：操作后应立刻看到结果。能实时改的绝不重启；必须重启的要提示「正在应用」，并显式管理 `restarting`，避免按钮被误置灰。
- 界面需求先出线框或截图，确认后再写代码。
- 文档与实现同一次提交更新。发布包必须能回滚到上一版。

## 5. 三层测试

按 L1 单元 → L2 协议 → L3 真实 UI E2E 进行。L3 使用 `scripts/e2e_cast.ps1`，必须真实点击控件。禁止用「直接调插件 / 直接调内核」作为交付依据。

测试前必须隔离环境：杀掉旧进程、清理 `settings.json`、清理 WebView2。发布只允许 `npm run tauri -- build`，界面要显示版本号。发布包必须校验默认配置（如 `lockPosition=false`、`stayAwake=true`），测试产物不得打进 zip。

若 `scripts/gate.ps1` 尚不存在，不得声称门禁已通过，并在交付说明里标明。

## 6. DoD 与交付

对照 [references/dod-checklist.md](references/dod-checklist.md)，五条全部满足才能写入交付说明。交付前按用户路径自己走 3 遍：首次使用、二次使用、异常路径，并附证据。交付说明必须写清：本次能做什么、不能做什么、已知问题。

## 7. 措辞

禁止说「已修复」「应该可以了，你试试」。只能说「已验证（附截图、数值或日志）」或「已改，待验证」。

## 8. 复盘

现象 → 根因 → 规则，追加写入 `docs/retrospective-and-skill-rules.md`。

## 反面模式（出现即打回）

- 「应该可以了，你试试」
- 「参考了 XX 风格」但无截图、无对照表
- 用协议测试代替界面验收
- 新增控件却不删旧控件
- 核心代码出现业务名词
- 没有回滚路径的发布
- 把「命令成功 / 窗口出现」当成用户目标已达成
- 设置只写入文件、不作用于当前会话
